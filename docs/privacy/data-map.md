# 개인정보 데이터 맵 (잡카드)

> 기준: Phase 0.3 (2026-11-07). 코드가 바뀌면 이 문서도 같이 고친다 — 특히 `backend/privacy.py`, `backend/retention.py`, `backend/main.py`의 AI 호출부, `ai_service/schemas.py`.
> 법무 검토 전 초안이다. 보존기간의 법적 근거는 법무 검토로 확정해야 한다.

## 2. 저장 위치

| 데이터 | 위치 | 비고 |
|---|---|---|
| DB 전체 | SQLite `jobcard.db` (Docker named volume `jobcard-data`, `/app/data`) | WAL 모드. `secure_delete=ON`으로 지운 행을 0으로 덮는다. `journal_size_limit=0`으로 WAL 재시작 때 -wal 파일을 잘라 옛 프레임이 파일 뒤쪽에 남지 않게 한다 |
| TTS mp3 | `/app/data/tts/<hash>.mp3` | 단계 문장 음성. 파일명은 (사업장 id + 음성 옵션 + 문장) 해시 — 사업장끼리 캐시를 공유하지 않는다(Phase 0.3) |
| 단계 사진 | `/app/data/photos/<uuid>.webp` | 0004 이전 사진은 마이그레이션 때 메타데이터를 지운 WebP로 다시 저장하고, EXIF가 든 옛 원본은 그 자리에서 바로 지운다 |

**사진·TTS 접근(Phase 0.3)**: 예전에는 `/api/photos`, `/api/tts`가 인증 없는 정적 경로라 파일명만 알면 누구나 받을 수 있었다. 이제 정적 경로는 없고,
인증·소유권 검사를 통과한 API 응답에만 단기 서명 URL(`/api/media/{id}?exp=&sig=`, HMAC(JOBCARD_SECRET), 기본 수명
`MEDIA_URL_TTL_SECONDS`=3600초)이 실린다. 서명은 media id에 묶여 다른 파일에 쓸 수 없고, 만료·위조는 403이다. URL이 새면(화면 공유·브라우저 기록)
만료 전까지는 누구나 받을 수 있다 — 수명을 짧게 두는 이유다. 자체 AAC 그림(`/api/aac/images`)은 공개 자산이라 그대로 연다.
| 브라우저 | `localStorage`: 토큰, 역할, 표시 이름, 사업장 코드 | 공용 기기는 로그아웃 필요 |
| 내보내기 파일 | 사업주 PC(다운로드) | 서버에는 사본을 남기지 않는다 |

## 3. 외부 전송 (처리 위탁·국외 이전)

| 수신자 | 국가 | 언제 | 보내는 것 | 보내지 않는 것 |
|---|---|---|---|---|
| OpenAI (Chat Completions, `OPENAI_MODEL`) | 미국 | 직무 분해(`/ai/decompose`) | 직무 원문(근로자 이름 → "근로자 A" 별칭), 업종, 작업 환경, 근로자 특성 메모(**허용+동의 시에만**, 별칭 적용) | 근로자 실명, 근로자 id, 접속 코드 |
| OpenAI (Chat Completions) | 미국 | AI 코칭(`/ai/coaching`) | 직무 제목·단계 문장(별칭), 단계별 수행 수치, 업종·환경·직무 분류, 메모(**근로자 지정 + 허용 + 동의 시에만**) | 실명, 근로자 id. **AI 처리 동의가 없거나 철회된 근로자의 기록이 섞이면 LLM을 아예 부르지 않는다**(규칙 기반 제안) |
| OpenAI (Embeddings, `OPENAI_EMBED_MODEL`) | 미국 | 그림(AAC) 검색 | 단계 문장·검색어(별칭 적용) | 메모, 실명 |
| Google Cloud Text-to-Speech | 미국 등 | 단계 음성 합성 | 단계 문장 **원문**(실명이 들어 있으면 그대로) | 근로자 정보 |

- 별칭 매핑은 `backend/privacy.py: Pseudonymizer`. 사업장 근로자 전원의 표시 이름을 등록 순서대로 "근로자 A, B, …"로 바꾸고 응답에서 되돌린다. 매핑은 요청 하나 안에서만 쓰고 저장하지 않는다.
- 한계 1(놓침): 등록된 표시 이름과 **글자가 똑같을 때만** 바꾼다(라틴 문자 이름은 대소문자 무시). 성을 뺀 이름·별명은 못 잡는다. 기본 이름 "근로자" 같은 일반 명사는 바꾸지 않는다.
- **3음절 이상 한글 이름·띄어쓰기가 든 이름은 앞뒤를 보지 않고 부분 문자열로 모두 바꾼다(fail-closed).** 예전에는 아래 경계 규칙(허용 목록)을 모든 이름에 써서, 목록에 없는 꼴("김민지에겐", "김민지라서", "김민지면", "팀장김민지가", "김민지와박지수")의 실명이 그대로 OpenAI로 갔다(3차 검증). 이제 "홍길동동"처럼 이름을 품은 다른 낱말도 바뀌지만, 분해 품질 손해가 실명 유출보다 작다고 봤다. 라틴 문자 이름은 앞뒤에 라틴 글자가 붙지 않았을 때 바꾼다("John에겐"은 바꾸고 "Johnson"은 그대로).
- 한계 2(잘못 바꿈) 대응 — **2음절 한글 이름과 일반 낱말 이름에만 적용**: 이름이 아닌 낱말을 별칭으로 바꾸면 분해 입력·그림 검색 질의가 망가진다("하나씩" → "근로자 A씩"). 성으로 시작하는 2음절 낱말("정리"·"이상"·"조금")도 많아 2음절 이름은 부분 문자열로 바꾸지 않는다. 그래서
  - 이름 바로 앞에 글자가 붙어 있으면 바꾸지 않고, 이름 뒤는 끝·공백·구두점이거나 호칭·조사·어미 조각(`privacy._TAIL_PIECES`: 씨·님·네·에게·한테서·께서·는·도·요·였·어요 …)이 **최대 4개까지 겹쳐** 이어지다 끝날 때 바꾼다("김민지에게는", "김민지님께서는", "김민지는요", "김민지네"). 목록에 없는 조각이 붙으면("민지동") 다른 낱말로 보고 그대로 둔다. 줄임꼴·구어체(에겐·한텐·께선·라서·면·잖아·니까·거·것 …)도 목록에 있다. **남은 위험**: 2음절 이름은 목록에 없는 꼴과 앞에 글자가 붙은 꼴("팀장민지가")을 여전히 놓칠 수 있다 — 새로 발견되면 목록에 더한다.
  - 일반 낱말·수사와 같은 이름(`privacy.COMMON_WORD_NAMES`: 하나·보람·나라·슬기·한결 등)은 "하나 씨"·"하나님께"처럼 **호칭이 붙은 경우만** 바꾼다. 그 밖의 "하나가"는 이름이어도 그대로 나간다(놓침 쪽으로 기운 선택). 근로자 관리 화면이 이런 이름에 경고를 띄운다(`WorkerOut.name_ambiguous`).
  - 목록에 없는 이름도 "낱말 + 조사" 꼴과 겹치면 바뀔 수 있다. 매칭 평가(`eval.run_match_eval`)는 백엔드 마스킹을 거치지 않으므로 이 회귀는 `backend/tests/test_privacy.py`가 잡는다.
- 되돌리기: LLM이 "근로자A"처럼 띄어쓰기를 바꿔도 되돌린다. **이 요청에서 `mask()`가 실제로 만든 별칭만** 실명으로 되돌린다. 사업주가 원문에 직접 쓴 별칭 모양의 글("근로자 B")은 응답에 돌아와도 그대로 둔다(예전에는 "근로자"로 바꿔 사업주 글을 고쳤다). 남은 위험: 사업주가 직접 쓴 "근로자 A"와 실제로 만든 별칭 "근로자 A"가 한 요청에 함께 있으면 구분할 수 없어 실명으로 되돌린다. 그 밖에 이 요청에서 만들지 않은 한 글자 별칭("근로자 Q", 원문에 없던 근로자의 별칭)은 화면·TTS에 나가지 않게 "근로자"로 바꾸고 경고 로그를 남긴다. 두 글자 이상 대문자("근로자 ID"·"근로자 OK")는 실제로 만든 별칭(근로자 AA …)일 때만 되돌리고, 아니면 평범한 문장으로 보고 그대로 둔다.
- ai_service는 스키마(`DecomposeContext`, `CoachingContext`, 그림 매칭·검색용 `SymbolContext`)로 허용한 필드만 받고 나머지(예: `worker_name`)는 버린다. 분해 로그에는 원문 대신 길이만 남긴다.
- **남은 위험**: Google TTS는 사람이 듣는 문장이 그대로 필요해 별칭을 쓸 수 없다. 사업주에게 "단계 문장에 이름을 넣지 말 것"을 안내한다. TTS 위탁에 대한 동의 범위는 법무 검토가 필요하다.

## 4. 동의

| 종류(`consent_type`) | 의미 | 없으면 |
|---|---|---|
| `personal_info` | 서비스 제공을 위한 개인정보 수집·이용 | (기록만. 현재 기능 제한 없음 — 운영 정책으로 등록 전 수령). 근로자 관리 화면에서 기록·철회한다(`WorkerOut.personal_info_consent`) |
| `ai_processing` | AI 코칭을 위한 처리 위탁·국외 이전(OpenAI) | 그 근로자 기록은 LLM 코칭에서 제외, 메모 전송 안 함 |

- 주체: `self`(당사자) / `guardian`(보호자·법정대리인). 동의서 원본은 사업장이 보관하고 서버에는 수령 사실·방침 버전(`PRIVACY_POLICY_VERSION`)·기록한 사업주·일시만 남긴다.
- 철회는 행을 지우지 않고 `revoked_at`을 채운다(유효 기간의 근거). 근로자 삭제 시에는 동의 기록도 지운다.

## 5. 보존기간과 삭제

| 데이터 | 보존 | 삭제 방법 |
|---|---|---|
| 수행 로그 | `PERFORMANCE_LOG_RETENTION_DAYS` (기본 365일, `completed_at` 기준) | scheduler가 매일 `purge` (아래 "삭제 스케줄") |
| 도움 요청 | 수행 로그와 같은 `PERFORMANCE_LOG_RETENTION_DAYS` (기본 365일, `created_at` 기준) | scheduler가 매일 `purge`(결과의 `help_requests` 개수). 근로자를 지우면 함께 지우고, 직무를 지우면 그 배정의 요청을 지운다. 단계만 지우면 기록은 남기고 `step_id`를 비운다 |
| 화면 설정·마지막 접속 | 근로자 프로필과 같이(사업주가 삭제할 때까지) | `DELETE /api/workers/{id}` |
| 접근 감사 로그 | `ACCESS_AUDIT_RETENTION_DAYS` (기본 730일) — 「개인정보의 안전성 확보조치 기준」 제8조: 민감정보 처리 시 접속기록 2년 이상 | scheduler가 매일 `purge` (앱 코드에 다른 삭제·수정 경로 없음) |
| TTS mp3 | 단계를 지우거나 문장을 고치면 그 단계의 소유 레코드는 바로 지운다. 파일은 어느 레코드도 가리키지 않게 된 뒤 `MEDIA_ORPHAN_GRACE_HOURS`(없으면 `TTS_ORPHAN_GRACE_HOURS`, 기본 24시간) 뒤. 캐시를 다시 쓰면 수정 시각을 갱신하고, 정리는 지우기 직전에 레코드·시각을 다시 확인한다(재사용과의 경합 방지) | `manage.py purge` 또는 `manage.py gc-media` |
| 단계 사진 | 사진을 교체·되돌리거나 단계·직무를 지우면, 다른 단계가 쓰지 않는 한 레코드와 파일을 **바로** 지운다. 레코드 없는 파일(업로드 중 실패 등)은 유예시간 뒤 | 즉시(API) + scheduler의 매일 `purge`(`gc-media`와 같은 정리) |
| 근로자 프로필·메모·배정·수행 로그·동의·도움 요청 | 사업주가 삭제할 때까지 | `DELETE /api/workers/{id}` — DB 행 삭제 + `secure_delete` + WAL 체크포인트(아래 "WAL 체크포인트") |
| 직무 원문·제목·단계 문장 속 근로자 이름, 그 문장의 TTS mp3 | **근로자를 삭제해도 남는다**(직무는 사업주 데이터) | 직무를 고치거나 지워야 사라진다. 삭제 응답의 `name_mentions`와 삭제 확인 대화상자가 이를 알린다. 문장을 고치면 옛 mp3는 미참조가 되어 purge가 지운다 |
| 직무·단계·사진 | 사업주가 직무를 삭제할 때까지 | `DELETE /api/tasks/{id}` — 단계 행과 그 사진(다른 직무가 쓰지 않으면)·TTS 레코드를 함께 지운다 |
| 배정(`assignments`) | 근로자·직무 삭제 때까지 | 보존기간 자동 삭제 없음 — 후속 과제 |
| 백업 | 운영자가 정함 | 백업 사본에는 삭제가 반영되지 않는다 — 백업 보존기간을 별도로 정해야 한다 |
| 마이그레이션 자동 백업(`<DB 폴더>/backups/jobcard-<시각>-<리비전>.db`, compose는 `/app/data/backups`, `JOBCARD_BACKUP_DIR`) | 마이그레이션이 성공하고 서비스가 정상인 것을 확인한 뒤 **30일 안** | `manage.py migrate`가 upgrade 전에 DB 전체(근로자 이름·메모·접속 코드 암호문·수행 기록)를 복사한다. 근로자 삭제·`purge`가 이 사본을 지우지 않으므로 운영자가 손으로 지운다. `purge`가 지난 사본을 지우는 일은 후속 과제 |

### WAL 체크포인트

지운 행의 옛 내용은 WAL(-wal 파일) 프레임에 남는다. 삭제 직후 `PRAGMA wal_checkpoint(TRUNCATE)`로 DB 파일에 옮기고 -wal을 0바이트로 자른다.
다른 연결이 읽기 트랜잭션을 잡고 있으면(예: 대시보드 3초 폴링) 체크포인트가 끝나지 않는다. 이때 옛 프레임은 **저절로 덮이지 않는다** —
WAL을 재시작해도 파일을 자르지 않으면 새로 쓴 지점 뒤의 옛 프레임은 물리적으로 남는다. 그래서
- `database.checkpoint_wal`이 결과 `(busy, log, checkpointed)`를 확인해 짧게 다시 하고, 그래도 안 되면 경고 로그를 남긴다.
- 삭제 응답에 `wal_checkpointed: false`를 실어 화면이 알린다.
- 매일 도는 `manage.py purge`가 지울 것이 없어도 TRUNCATE 체크포인트를 다시 한다(실패하면 출력에 경고).
- `journal_size_limit=0`으로 WAL이 재시작될 때마다 파일을 자른다.

### 사진·TTS 보존 정책: 참조되는 동안 보존, 고아만 정리

사진·TTS 파일에는 **날짜 기준 보존기간이 없다.** 어느 단계가 가리키는 동안은 직무의 일부라 그대로 두고
(근로자가 매일 보는 그림·음성이 어느 날 사라지면 안 된다), **어느 단계도 가리키지 않게 된 것(고아)만** 지운다.

- 고아가 되는 때: 사진 교체·되돌리기, 단계 문장 수정(옛 TTS), 단계·직무 삭제. 사진은 그 자리에서 바로 지우고,
  TTS 파일과 레코드 없는 파일(업로드·생성 도중 실패)은 `MEDIA_ORPHAN_GRACE_HOURS`(기본 24시간) 유예 뒤 매일 정리가 지운다.
- 근로자를 지워도 직무의 사진·TTS는 남는다(직무는 사업주 데이터, 위 표). 직무를 고치거나 지워야 사라진다.
- 사업주가 직무를 오래 두면 사진·TTS도 그만큼 남는다. 직무 자체의 보존기간은 아직 없다(후속 과제, 배정과 같이).

### 삭제 스케줄

compose 기본 프로필의 `scheduler` 서비스(backend와 같은 이미지, `python manage.py schedule`)가
마지막 성공 후 `PURGE_INTERVAL_HOURS`(기본 24시간)마다 `purge`를 한 번 돌린다 — 보존기간이 지난 수행 로그·
접근 감사 로그 삭제, 고아 사진·TTS 정리(`gc-media`와 같은 일), WAL 체크포인트. 실패하면
`PURGE_RETRY_MINUTES`(기본 60분) 뒤 다시 한다. `docker compose up`이면 같이 뜨므로 예전처럼 호스트 crontab에
등록할 필요가 없다(등록을 잊으면 개인정보가 보존기간을 넘겨 남는데 아무 데서도 드러나지 않았다).

- 요청을 받는 backend 안에 두지 않는다(backend를 여러 개 띄우면 같은 삭제가 겹친다). `scheduler`도 **하나만** 띄운다.
- 마지막 성공 시각은 공유 볼륨의 `PURGE_STATUS_FILE`(`/app/data/maintenance/purge_status.json`)에 남고, backend
  `GET /health`가 `purge.last_success_at`·`age_hours`·`stale`(주기의 1.5배를 넘김 또는 한 번도 성공 안 함)·
  `last_error`(오류 종류만, 메시지 없음)로 보여 준다. 모니터링은 `purge.stale == true`를 경보로 쓴다.
  `stale`이어도 `/health`의 `status`는 `ok`다(삭제가 밀렸다고 API까지 내리지 않는다).
- 실행 기록·지운 개수: `docker compose logs scheduler`.
- 손으로 돌리기·확인만 하기: `docker compose --profile maintenance run --rm purge` /
  `docker compose --profile maintenance run --rm purge python manage.py purge --dry-run`. 손으로 돌린 purge도
  성공하면 마지막 성공 시각을 갱신한다(dry-run은 갱신하지 않는다).

## 6. 접근 감사

`access_audit_logs`에 남기는 행위(`action`):

| action | 언제 |
|---|---|
| `worker.list` | 근로자 목록 조회 (목록에 실린 근로자마다 한 줄) |
| `worker.history` | 근로자별 배정 직무·활동일 조회 |
| `worker.update` | 근로자 이름·메모·AI 메모 허용 변경 |
| `worker.consents` / `worker.consent.grant` / `worker.consent.revoke` | 동의 조회·기록·철회 |
| `worker.export` | 데이터 내보내기 |
| `worker.delete` | 근로자 삭제 (이후에도 id만 남는다) |
| `dashboard.workers` / `dashboard.view` | 대시보드 근로자 목록·근로자별 수행 기록 |
| `coaching.view` | AI 코칭 조회 |
| `help.list` | 사업주 화면 도움 알림 띠 조회(띠에 실린 근로자마다 한 줄, 5초 폴링은 묶는다) |
| `task.recipients` | 보내기 시트의 받는 사람 고르기(오늘 이 직무 배정이 있어 진행 상태가 실린 근로자마다 한 줄) |

- 화면이 저절로 되풀이하는 조회(`dashboard.view`, `dashboard.workers`, `worker.list`, `worker.history`, `worker.consents`, `coaching.view`, `help.list`, `task.recipients`)만 같은 사업주·행위·근로자·IP가 `ACCESS_AUDIT_DEDUPE_SECONDS`(기본 60초) 안에 반복되면 한 줄로 합친다(대시보드 3초 폴링). 내보내기·삭제·동의 기록·수정은 매번 남긴다.
- 근로자 목록(`worker.list`)과 근로자를 고르지 않은 집계 화면(`dashboard.workers`, 근로자 미지정 `dashboard.view`·`coaching.view`)은 화면에 실린 근로자마다 한 줄씩 남긴다(`worker_id=None` 한 줄로는 누구의 기록이 보였는지 알 수 없다). 실린 근로자가 없으면 `worker_id=None` 한 줄만 남긴다.
- 다른 사업장 근로자 id로 대시보드·코칭을 열면 404이고 감사 행을 남기지 않는다.
- ORM으로 수정·삭제하면 예외가 난다(`models.py` 매퍼 이벤트). 지우는 코드는 `retention.py`뿐이다(테스트가 확인).
