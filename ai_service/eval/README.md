# 평가 하네스 (점수판)

눈대중 대신 정량으로 개선/회귀(regression)를 잡는 도구. 두 개가 있고, 파이프라인의
서로 다른 절반을 잰다.

| 하네스 | 질문 | 실행 |
|--------|------|------|
| `run_eval.py` | 문장을 **잘 나눴는가** | `python -m eval.run_eval` |
| `run_match_eval.py` | 그 문장에 **맞는 그림을 골랐는가**(정해진 골든셋 기준) | `python -m eval.run_match_eval` |
| `blind_test.py` | 그 그림이 **처음 보는 실제 문장에도** 맞는가(내가 안 짠 시험지) | `python -m eval.blind_test` |

# 1. 직무 분해 평가 하네스

프롬프트(`llm.py`의 `_DECOMPOSE_SYSTEM`)를 바꿀 때마다 분해 품질을 **점수**로 확인한다.

## 실행

```bash
cd ai_service

# 전체 채점
python -m eval.run_eval

# 특정 케이스만
python -m eval.run_eval --case cafe_close

# 점수를 JSON으로 저장(프롬프트 전/후 비교용)
python -m eval.run_eval --json before.json
# ...프롬프트 수정 후...
python -m eval.run_eval --json after.json
```

## 두 가지 동작 모드

| 모드 | 조건 | 의미 |
|------|------|------|
| **LLM** | `OPENAI_API_KEY` 설정됨 | 실제 LLM 분해를 채점 → 프롬프트 개선 효과 측정 |
| **규칙기반 폴백** | 키 없음 | 폴백 분해를 채점. `symbol_query`가 비어 LLM 전용 지표는 낮게 나옴 → **점수 하한선**(LLM이 왜 필요한지 보여줌) |

> 프롬프트 개선 효과를 보려면 `OPENAI_API_KEY`를 설정하고 돌려야 한다.

## 채점 기준 (rubric)

`dataset.json`의 `rubric_weights`로 가중치를 조절한다.

| 지표 | 측정 |
|------|------|
| `steps_in_range` | 기대 단계 수 범위 안인가 |
| `sentence_brevity` | 문장이 권장 글자수(`brevity_max_chars`, 기본 20자) 이내 비율 |
| `imperative_ending` | 명령형(`~요/~세요/~다`)으로 끝나는 비율 |
| `symbol_query_quality` | 단계별 `symbol_query`에 한글+영어가 함께 있는 비율 (LLM 지표) |
| `action_typed` | `action_type`이 `other`가 아닌(구체 분류된) 비율 |
| `keyword_coverage` | 기대 키워드가 결과에 등장하는 비율 |

## 정답셋 늘리기

`dataset.json`의 `cases` 배열에 추가:

```json
{
  "id": "고유_id",
  "domain": "cafe 또는 office",
  "raw_input": "사업주가 입력하는 원문 직무 지시",
  "context": {"business_type": "카페", "work_environment": "홀"},
  "expect": {
    "min_steps": 3,
    "max_steps": 4,
    "must_have_keywords": ["꼭 등장해야 할 단어"]
  }
}
```

# 2. AAC 이미지 매칭 평가 하네스

매칭 스코어러(`local_aac.py`)를 고칠 때마다 돌려서 개선/회귀를 숫자로 확인한다.
**네트워크·LLM을 쓰지 않으므로 API 키 없이 항상 같은 결과가 나온다(결정적).**

## 실행

```bash
cd ai_service

python -m eval.run_match_eval                       # 전체 채점
python -m eval.run_match_eval --query-mode sentence # 규칙 폴백 경로
python -m eval.run_match_eval --job cleaning        # 특정 직무만
python -m eval.run_match_eval --case cafe_sweep     # 특정 케이스만
python -m eval.run_match_eval --verbose             # 케이스별 상위 후보까지
python -m eval.run_match_eval --sweep               # 임계값 절충 곡선

# 스코어러 수정 전/후 비교
python -m eval.run_match_eval --json before.json
# ...local_aac.py 수정 후...
python -m eval.run_match_eval --json after.json
```

## 두 가지 질의 모드

프로덕션에 실제로 존재하는 두 경로를 각각 잰다.

| 모드 | 질의 | 재현하는 경로 |
|------|------|---------------|
| `full` (기본) | 문장 + `symbol_query` | LLM 분해 성공 |
| `sentence` | 문장만 | LLM 키 없음/실패 → 규칙 폴백 (점수 하한선) |

## 지표

| 지표 | 측정 | 방향 |
|------|------|------|
| `top1_accuracy` | 1순위가 정답 집합에 있는 비율 | ↑ |
| `recall@3` | 상위 3개 안에 정답이 있는 비율 → **사람에게 후보를 보여줄 때의 상한** | ↑ |
| `recall@20` | 상위 20개 안에 정답이 있는 비율 → **리랭커를 붙였을 때의 상한** | ↑ |
| `wrong_accept_rate` | 정답이 아닌데 자동 채택한 비율 — **현장에 오답 카드가 나가는 비율** | ↓ **가장 중요** |
| `gap_declined_rate` | 정답 자산이 없는 케이스를 올바르게 거절한 비율 | ↑ |
| `handoff_rate` | 자동 채택하지 않고 넘긴 비율(사람 확인 필요) | 낮되 0은 아님 |

보고서는 거절 사유 분포도 함께 낸다. `low_margin`(후보는 있는데 못 고름)과
`low_score`/`no_candidate`(쓸 만한 후보가 없음)는 검토 화면에서 다르게 다뤄야 한다 —
전자는 후보를 보여주고 사람이 고르게, 후자는 폴백이나 실제 현장 사진으로.

`top1_accuracy`만 보지 말 것. **오답을 확신에 차서 채택하는 것**이 거절하는 것보다
훨씬 나쁘므로 `wrong_accept_rate`가 1차 지표다.

`full` = 문장+symbol_query, `sentence` = 문장만.

- job 일치 `+0.16`/불일치 `-0.08` → `+0.02`/`-0.01`, asset_type `±0.04` → `±0.015`.
  경계 사례의 실측 관련도 격차(0.02 내외)를 기준으로 정했다.
- `group_id` 변형과 동일 라벨 중복을 결과에서 제거.
- 점수 척도가 낮아져 임계값을 `--sweep`으로 0.28 → 0.18 재교정.
- **오답 채택이 거의 절반으로**(0.126→0.069, 0.149→0.115). `top1`은 그대로, 회귀 0건.

**2026-09-10 — `action_type` 배선 + 포함 점수 길이 정규화**

- `backend/main.py`의 두 호출 지점이 `action_type`을 AAC 검색에 넘기지 않았다.
  `add_step`은 context를 아예 안 넘겨 문장조차 쓰이지 않았다. 둘 다 수정.
- **배선만 고쳤더니 오답 채택이 오히려 악화됐다**(0.069→0.092). `±0.015` 동점 보정으로는
  도구가 동작을 이기는 격차를 못 넘으면서, 점수만 올려 임계값을 더 통과시켰기 때문이다.
- 격차를 실측하니 ~0.08로 일정했고, 이는 `containment` 항의 가중치(0.08)와 일치했다.
  원인은 **포함 점수가 길이를 무시한 것** — `"행주" in "테이블을 행주로 닦아주세요"`가
  참이라 한 단어 도구 라벨이 언급되기만 해도 만점을 받았다. 짧은 쪽이 긴 쪽을 덮는
  비율로 정규화했다.
- **`top1` 0.878→0.915, 오답 채택 0.069→0.023.** 도구가 동작을 이기던 실패
  (`cafe_table_wipe`·`clean_tissue`·`clean_car_sponge`)가 모두 사라졌고, 남은 1순위 오답
  7건 중 5건은 이제 자동 채택 대신 **거절**된다.
- 점수 척도가 다시 바뀌어 임계값을 0.18 → 0.20으로 재교정.

**2026-09-10 — margin 게이트 (`local_aac.decide`)**

- 절대 임계값 하나 대신 두 조건을 함께 본다: 1순위 점수 ≥ 임계값 **그리고**
  1순위−2순위 ≥ 여유. 붙어 있는 후보 중 아무거나 고르지 않는다.
- 거절 사유를 `no_candidate` / `low_score` / `low_margin`으로 구분해 돌려주고,
  거절해도 후보 목록은 함께 준다. `low_score`는 폴백, `low_margin`은 후보를 보여주고
  사람이 고르는 경로다.
- `--sweep-margin`(임계값 × 여유 2차원)으로 교정해 **임계 0.14 / 여유 0.02** 선택.
  여유 게이트가 있으면 임계값을 더 낮춰도 오답이 안 늘어난다.
- **두 모드 모두 오답 채택 0.023, 갭 거절 1.000.** 폴백 경로의 오답 채택이
  0.092 → 0.023으로 4배 개선됐다(이전에는 `full`만 좋고 `sentence`가 나빴다).
- 거절 26건 중 **22건이 `low_margin`**(후보는 있는데 못 고름), 4건만 폴백.
  `recall@3` 0.988이므로 후보 3개를 보여주면 거의 항상 정답이 들어 있다
  → 검토 화면 후보 선택 UI로 이어졌다(아래).

**2026-09-11 — 검토 화면 후보 선택 UI**

`low_margin`으로 거절된 단계를 폴백으로 버리지 않고 사업주가 직접 고르게 한다.

- `map_symbols`가 `reason`과 `candidates`(상위 3개)를 함께 반환.
- 백엔드 `GET /api/tasks/{id}/steps/{sid}/symbol-candidates` — 후보를 저장하지 않고
  그때그때 다시 검색한다. 단계 문장이 바뀌면 후보도 바뀌어야 하는데, 컬럼으로 들고 있으면
  문장과 어긋난 채 굳는다.
- 후보를 고르면 `symbol_source`가 `LOCAL_AAC`로 남는다(예전에는 무엇을 고르든
  `fallback`으로 적혀 출처를 알 수 없었다).
- 후보가 없으면(`low_score`/`no_candidate`) 실제 현장 사진을 권한다.

이 UI는 매칭 지표를 바꾸지 않는다 — `wrong_accept_rate`는 자동 채택만 세고, 후보 선택은
사람이 하는 일이다. 지표상 `handoff_rate` 0.299가 '폴백 26건'에서 '사람이 3개 중 고르는
22건 + 폴백 4건'으로 바뀐 것이 이 작업의 효과다.

관대했다.** v1의 갭 5건이 전부 타 업종 문장이라 업종 가중치만으로 걸러졌기 때문이다.

같은 업종 안에서 정답 자산이 없는 문장을 15개 만들어 재보니 **8건이 오답으로 자동 채택**됐다.
그중 자산 부재를 라벨로 직접 확인한 14건을 정답셋에 넣었다.

- `wrong_accept_rate` 0.023 → **0.079** (실제로는 3.4배 나빴다)
- `gap_declined_rate` 1.000 → **0.684**

**드러난 실패 유형 — 도구/보조 카드가 문장의 명사와 같으면 그대로 채택된다:**

| 갭 문장 | 채택된 오답 | 점수 |
|---------|------------|------|
| 작업 지시서를 복사하세요 | 작업 지시서 (support) | 0.332 |
| 커피머신 전원을 켜세요 | 커피머신 (tool) | 0.278 |
| 대걸레를 새것으로 바꾸세요 | 대걸레 (tool) | 0.231 |

포함 점수 정규화로 "행주" 유형은 잡았지만, 문장의 **주어가 곧 도구 이름**이면 여전히 뚫린다.
`_ASSET_TYPE_TIEBREAK`(±0.015)로는 못 막는다 — 이 격차는 0.05~0.15다. 도구 카드는

못한다. 자산을 `동작+대상+도구` 구조로 만들어야 풀린다.

**2026-09-11 — 구조화 인덱스를 매칭에 연결**

`aac_index.json`을 런타임이 읽게 하고, 네 가지를 한 번에 하나씩 적용하며 매번 측정했다.

1. **인덱스 검색어 병합** — 라벨에 이어 붙였더니 Jaccard 분모가 커져 **모든 점수가
   희석**됐다(full top1 0.915 → 0.732). 검색어가 많은 자산일수록 손해를 본다.
   라벨과 검색어를 따로 재고 `max`를 쓰도록 고쳤다.
2. **사물 카드 게이트** — 지시문("얼음통을 씻어주세요")에는 도구 그림이 아니라 동작
   그림이 맞다. 종결어미로 지시문 여부를 보고 사물 카드 관련도를 0.55배로 깎는다.
   이전의 `_ASSET_TYPE_TIEBREAK`(±0.015)로는 못 막았다 — 실측 격차가 0.05~0.15였다.
3. **동사 계열 호환성** — 정답 쌍을 실측하니 둘 다 구체적인 66건 중 55건이 일치,
   11건이 불일치였다(`move/pack/sort` 계열에 몰림). 그래서 하드 페널티 대신 0.85배
   완만한 벌점을 주고, 그 계열은 호환으로 묶었다.
4. **동사 원형 직접 매칭** — 이게 결정적이었다(아래).

### 인덱스의 값어치는 키워드가 아니라 동사 원형에 있었다

키워드 가중치를 스윕해 보니 **`sentence` 모드가 완전히 무반응**이었다. 401개 항목을
만들었는데 지표가 1도 안 움직였다. 원인은 형태 불일치였다:

```
질의 "원두를 갈아주세요" → 토큰 {원두, 갈아주}
인덱스 검색어 "갈다"      → 토큰 {갈다}
교집합: 없음.  bigram 교집합: 없음.
```

검색어는 **사전형**인데 질의는 **활용형**이라 영영 만나지 못했다. 인덱스의 동사로
닫힌 사전을 만들어 활용형에서 원형을 되찾고(`_verb_lemmas`), 원형이 일치하면 Jaccard
가방을 거치지 않고 **직접 가산**(`_VERB_MATCH_BONUS`)하도록 바꾸자 `top1`이 두 모드
모두 0.939로 올랐다. 가방 안에서는 '갈다' 하나가 검색어 7개 중 1개로 계산돼 묻힌다.

반대로 **키워드 가방 유사도는 높을수록 해로웠다**(`_KEYWORD_WEIGHT` 0.9 → full top1
0.939, 0.6 → 0.951). 관련 없는 검색어까지 분모에 들어가 잡음이 된다. 그래서 0.6으로
낮췄다. 인덱스가 값어치를 하는 곳은 `_lemmas`와 `is_object_card`다 — 둘 다 가방이
아니라 직접 비교하는 신호다.

**2026-09-11 — 도구(instrument) 검색어 보강**

앱에서 확인한 문제: "대걸레로 닦으세요" 후보가 `[변기 솔 닦기, 밀대 바닥 닦기, 차체 스펀지
닦기]` — 정답 "밀대로 바닥을 닦는다"가 2순위. 청소 직무에서 "닦다"는 모든 자산에 있어
동사 신호가 잡음이 되고, "대걸레"가 자산 라벨의 "밀대"와 단어가 달라 못 만났다.

- `frame.instrument` 와 라벨에서 뽑은 도구 명사를 자산 검색어 바구니(`_kw_tokens`)에 넣고,
  도구 동의어 그룹(`대걸레↔밀대`, `수세미↔스펀지`, `빗자루↔비`)으로 질의 쪽도 넓힌다.
- 결과: "대걸레로 닦으세요"가 `밀대로 바닥을 닦는다` 1순위로, `low_score` → `low_margin`.
- **가산점은 안 준다.** `_TOOL_MATCH_BONUS` 0.06을 시도했더니 "수세미로 세면대를 닦으세요"가
  `차체를 스펀지로 닦는다`(세차)로 갔다 — 도구는 여러 동작에 공유돼서 밀어올리면 잡음이
  된다. 동사와 달리 '검색 가능하게'만 하고 순위는 Jaccard에 맡긴다.
- 하네스 지표는 거의 그대로(full top1 0.951 → 0.952). 골든셋에 동의어 경로 케이스가
  2건뿐이라 — `clean_mop_floor`, `clean_scrub_sponge` 추가.

- **남은 오답 유형은 대상(object) 구분이다.** "부품이 깨지지 않았는지 살펴보세요"에

## 채택 기준은 스윕으로 정한다

스코어러를 고치면 점수 척도가 바뀌므로 임계값과 여유는 **반드시 재교정**해야 한다.
눈대중으로 숫자를 찍지 말고 곡선을 보고 운영점을 고른다.

```bash
python -m eval.run_match_eval --sweep                  # 임계값 1차원
python -m eval.run_match_eval --sweep-margin           # 임계값 × 여유 2차원
python -m eval.run_match_eval --sweep-margin --query-mode sentence
```

환경변수 두 개가 기준이다.

| 변수 | 기본값 | 의미 |
|------|--------|------|
| `AAC_MATCH_THRESHOLD` | `0.14` | 1순위 점수가 이보다 낮으면 폴백 |
| `AAC_MATCH_MIN_MARGIN` | `0.02` | 1·2순위 점수 차가 이보다 작으면 사람에게 넘김 |

여유 게이트를 넣으면 **임계값을 더 낮춰도 오답이 늘지 않는다** — 점수가 낮아도
경쟁자가 없으면 확실한 답이고, 점수가 높아도 동점이면 확실하지 않기 때문이다.
단일 임계값으로는 이 구분이 불가능해서 권장 구간이 존재하지 않았다.

# 3. 블라인드 테스트 (`blind_test.py`)

## 왜 필요한가

`match_dataset.json`(위 2번 하네스의 골든셋)은 내가 코드를 보고 만들었고, 가중치도
그 골든셋으로 스윕해서 정했다. **시험 문제를 낸 사람이 자기 답안도 채점하는 구조라**,
골든셋 점수가 좋다고 실제로 정확하다는 보장이 없다. 실제로 지금까지 실사용 중
발견된 진짜 버그 3개(그림 없음 위양성, 업종 미입력, 반의어 채택 — 이 파일 위쪽
기록 참고)는 전부 골든셋이 아니라 사람이 앱을 직접 써보다가 나왔다. 골든셋은 그
버그들을 하나도 못 잡았다.

이 스크립트는 생성과 채점을 **둘 다 나(구현자)로부터 떼어낸다**:

1. **생성** — LLM에게 "이 앱이 뭘 하는지"만 알려주고 사업주 문장을 쓰게 한다.
   `verb_class`, margin 게이트, 반의어 목록 같은 내부 구현이나 알려진 약점은 프롬프트에
   절대 언급하지 않는다 — 내가 아는 약점을 문제 출제자가 알면 더 이상 블라인드가 아니다.
2. **실행** — 실제 운영 코드(`decompose` + `search_for_step_detailed`)를 그대로 돌린다.
3. **채점** — 또 다른 LLM 호출이 내부 점수·판정 사유를 못 보고 "문장과 그림 설명이
   뜻이 맞는지"만 본다.
4. **사람 검토** — LLM 채점도 틀릴 수 있으니, 불일치로 나온 것만 사람이 최종 확인한
   뒤 골든셋에 넣는다. **이 스크립트는 골든셋을 자동으로 고치지 않는다.**

## 실행

```bash
cd ai_service
export OPENAI_API_KEY=...            # 또는 저장소 루트 .env (AAC_DATA_DIR는 지워야 로컬 경로를 씀)
python -m eval.blind_test                    # 직무당 4문장(기본), 5직무
python -m eval.blind_test --per-job 8        # 더 많이
python -m eval.blind_test --job cafe         # 한 직무만
python -m eval.blind_test --json result.json # 결과 저장(커밋 안 함, .gitignore 처리됨)
```

매 실행마다 LLM이 새 문장을 만들어 결과가 매번 다르고 API 비용이 든다 — **그게

## 2026-09-16 위 "쓸다/쓰다" 열린 질문 확인 — 진짜 결함이었다, 그리고 근본 원인을 고쳤다

바로 위에서 "관측된 실패가 없어 보류"라고 적었는데, 확인해보니 실패가 있었다 —
같은 표면형 `쓰`에 원형이 두 개(`쓰다`/`쓸다`) 걸릴 때 `_verb_lemmas`가 **정렬에서
먼저 나온 것 하나만** 채택하고 있었다. 어느 쪽이 먼저 나오는지가 파이썬 set의 해시
순서에 달려 있어서, 실행할 때마다(서버를 재시작할 때마다) 결과가 바뀔 수 있는 상태였다.

- 실제로 재현됨: 이 문서 작성 시점 기준으로는 `쓸다`가 이겨서 "안전모를 쓰세요"
  (조립)가 `작업모를 쓰는 모습` 대신 아무 자산도 못 찾고 거절됐다(정답이 상위
  후보에 있는데도 점수가 안 나온 것 — 정답셋엔 이 정확한 문구가 없어서 지표엔
  안 잡혔다). 순서를 뒤집어 `쓰다`가 이기게 하니 이번엔 "바닥을 쓰세요"(청소)가
  `밀대로 바닥을 닦는다`(다른 동사)로 잘못 채택됐다. **한쪽을 고치면 반대쪽이
  깨지는 구조** — 어느 원형을 먼저 볼지 순서를 정하는 방식 자체가 틀렸다는 뜻이다.
- 근본 수정: `_verb_lemmas`가 동점(같은 길이) 어간에 걸리는 원형을 **하나만 고르지
  않고 전부** 후보로 남기도록 바꿨다(`바닥을 쓰세요` → `{쓰다, 쓸다}` 둘 다). 최종
  판단은 이미 `_score_asset`이 하고 있던 그대로 맡긴다 — 문맥(직무·명사 겹침)과
  안 맞는 쪽은 가산점을 받아도 다른 신호에서 지므로 저절로 걸러진다.
- **회귀 없이 개선**: `sentence` 모드 `top1_accuracy` **0.941 → 0.953**(다른 지표는
  불변). "안전모를 쓰세요"·"바닥을 쓰세요" 둘 다 정확한 자산으로 채택된다. 두
  방향을 각각 감시하는 카나리아를 추가했다 — 착용 쪽은 기존 `asm_goggles`(보안경을
  쓰세요)가 이미 있었고, 쓸기 쪽은 새로 `clean_sweep_polysemy` 추가.
- pytest 49/49 통과.

이 건은 처음에 "관측된 실패가 없다"고 판단한 게 **틀렸다** — 실제로 확인해보지 않고
"업종이 다르면 괜찮을 것"이라고 추론만 했던 것. 애매하면 추론으로 넘기지 말고
실제로 돌려봐야 한다는 걸 다시 확인했다.

| 품질 검사를 해주세요 | 조립 | 정상 거절(폴백) — 다만 같은 개념(확인)의 자산이 포장 직무에는 있다 |
| **재고를 확인해주세요** | 마트 | **오답 채택**("주문표를 확인한다", margin 0.041) |
| **메뉴판을 정리해주세요** | 카페 | **오답 채택**("상품을 한 줄로 정리한다", 마트 자산 — 직무도 틀림, margin 0.022) |

**결론**: "자산이 없으면 안전하게 폴백한다"는 항상 성립하지 않는다. `확인하다`/
`정리하다`처럼 인덱스에 흔한 범용 동사와 우연히 동사만 겹치면, 명사가 완전히
달라도(재고 vs 주문표, 메뉴판 vs 상품) 문턱을 겨우 넘는 오답이 나온다(둘 다 margin
0.02~0.04로 종이 한 장 차이). 두 사례 다 근본 수정 없이 `gap_retail_inventory_check`/
`gap_cafe_menu_organize`로 정답셋에 고정했다 — `확인하다`는 40여 건에 걸친 이
인덱스의 가장 흔한 동사라, 여기에 손대는 건 "명사 불일치 감점"류의 광범위한 수정과
같은 위험군이다(세 번 회귀한 패턴).

**방향 결정이 필요한 지점**: 이 갭을 메우려면 재고 조사·문서 작성·정산처럼 지금
자산에 아예 없는 새 개념을 위한 **새 픽토그램(이미지) 제작**이 필요하다 — 코드
수정이 아니라 콘텐츠 제작 범위의 일이다. 대안은 이런 사무적 지시문은 애초에
"사진 권장" 폴백으로 안내하는 게 맞는 설계라고 명시적으로 받아들이는 것. 둘 중
방향을 정해야 다음 작업(자산 추가 vs 폴백 문구 다듬기)이 정해진다.

## 2026-09-16 실사용 E2E 테스트에서 "의자 정리→상품 정리" 오답 발견·수정

실제 백엔드+ai_service 스택을 띄워(Docker 재빌드) 새 시나리오 5개를 `/api/tasks`로
직접 넣어 실제 매칭 결과를 확인했다(LLM 분해 경로). 9건 자동 채택 중 1건이 진짜
오답이었다: "의자들을 정리하세요."(청소 맥락)가 정답 `CAFE_078`("의자를 테이블에
맞춰 놓는다")이 후보 3위 안에 있는데도(`0.1989`), 명사가 전혀 다른 `CAFE_060`
("상품을 한 줄로 정리한다", `0.2209`)에 **margin 0.0204로 겨우 이겨** 자동
채택됐다.

**원인 — 앞서 고친 것들과 달리, 가중치가 아니라 스테밍(어미 제거) 버그였다.**
`_stem_token`의 어미 목록에 활용형 `한다`는 있는데 원형 `하다`가 없었다:
`"정리한다"→"정리"`(정상)인데 `"정리하다"→"정리하"`(끝 글자 하나가 안 떨어짐).
인덱스의 검색어는 원형(`keywords_ko: ["정리하다"]`)을 많이 쓰고 질의는 활용형
(`"정리하세요"→"정리"`)이라, 뜻이 같은데 토큰이 달라 안 만났다. `CAFE_078`의
검색어 `정리하다`가 `정리하`로만 남아 질의의 `정리`와 못 만난 반면, `CAFE_060`은
**라벨 자체**에 `정리한다`가 있어 이 버그와 무관하게 정상적으로 `정리`를 얻어
유리했다 — 순전히 우연한 비대칭이었다.

- 수정: 어미 목록에 `하다`를 `한다`보다 먼저 추가(`"하세요","해주세요","합니다",
  "하십시오","하다","한다",...`) — 순서가 중요하다, 먼저 걸려야 한다.
- **이건 새 가산점/벌점이 아니라 기존 정규화의 빠진 경우를 채운 것**이라, 이전에
  세 번 회귀했던 "명사 불일치 감점"류(frame.object 가산점, specificity 페널티)와는
  다른 종류의 수정이다.
- 골든셋(114케이스) **완전히 무변화** — 이 정확한 상황(정답이 키워드로만 걸리고
  라벨엔 없는데, 경쟁자가 라벨에 그 동사를 그대로 가진 경우)이 기존 정답셋에
  없었다는 뜻이다. 대신 실측 확인: `CAFE_060` 0.2209(불변) vs `CAFE_078`
  0.1989→**0.2154**로 개선 — **자동 오답 채택(`accepted`)에서 후보 경합
  (`low_margin`, 사람이 고름)으로 전환**됐다. 여전히 1위는 아니지만(margin 0.0055)
  더는 몰래 틀린 그림이 나가지 않는다.
- 이 케이스를 `cafe_chair_organize`로 정답셋에 추가(115케이스, `top1_accuracy`가
  0.965→0.954로 보이는 건 회귀가 아니라 이 케이스가 여전히 top1은 못 이겨서다 —
  `wrong_accept_rate`는 불변).
- pytest 49/49 통과.

**남은 질문**: "하다" 어미 정규화가 다른 "-하다" 원형 검색어(인덱스에 아주 흔함 —
확인하다·이동하다·시작하다 등)에도 비슷한 방식으로 도움이 될 수 있는지는 이번
골든셋에서는 안 드러났다(다른 케이스가 전부 불변이었다). 전체 401개 자산에 걸친
영향은 이번 한 건 재현으로는 다 보이지 않으니, 다음 블라인드 테스트 라운드에서
비슷한 패턴("동사가 원형으로만 인덱스에 있고 질의는 활용형인 정상 케이스")이 더
있는지 지켜볼 것.
